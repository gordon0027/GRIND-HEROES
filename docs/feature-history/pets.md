# Pet System V1–V2

## V1 implementation

Pet ownership is represented by three nontradable, stackable iDos Items. The native Store offers grant exactly one Item and have a per-player `TotalCap: 1`; the same Store transaction consumes GOLD, GEMS, or `CryptoCurrencies.Main`. The client never grants pet Items. `grind_pets_v1` is a ReadOnly UserCustomData JSON key containing the equipped ID and an optional pending ID. CloudCode checks actual Item counts before accepting any selection. A removed Item loses its bonus even if the protected selected ID remains.

There is one account pet, shared by the current formation. A selection during an active server run stays pending; `startStageRun` applies it at the next boundary and returns the chosen ID to the client. Combat and the server Team Power/Top 100 projection add the same flat Attack and HP values **after** archetype scaling and gear, once per active hero. `powerFormula.js`, caps, and gear slots are unchanged. The three names, test prices, bonuses and asset keys in `server/pets.js` are provisional. Store config owns the actual charge; `resolvePetOffer` refuses an offer that does not match the server catalog. `PetsSection` maps asset keys to `null` placeholders, ready for final PNG paths.

DEV title `98JRCAKG-DEV` has all three Item definitions, one-time Store offers, protected key, and CloudCode revision 32 with pet and Team Power handlers. GOLD and GEMS purchases, repeat rejection, ownership checks, queued selection, unequip, and leaderboard changes passed live DEV guest probes. DEV has no `Currency.CryptoCurrencies.Main`; a direct GH offer purchase returns `CC Main: not found in definitions`. GH spend and a relogin/device persistence check are still unverified. No pet configuration or CloudCode was uploaded to PROD. Before PROD release, establish a GH-capable safe test environment, verify the native Store crypto charge without spending a real PROD account's GH, and merge pet handlers into the current PROD revision while preserving its GH payout maintenance guard and existing handlers.

## V2 animated companions and TEAM UI

V2 keeps the same Item, Offer and pet IDs, prices and bonuses, but names them Donkey, Pug and Watchdog. The six supplied PNGs are local assets under `public/assets/pets/`. Each 12×4 sheet has its own frame size: Donkey 157×128, Pug 91×77, Watchdog 142×118. Rows are idle, run, attack and falling/defeat, with no empty frames. `petVisuals.ts` holds frame geometry, animation speed and formation offsets. A single Phaser `PetActor` follows the first living hero, approaches only a live encounter enemy and attacks visually without adding damage or camera/formation state. Defeat plays only when the full run fails. The actor is recreated at a run boundary or server-confirmed pet change. TEAM contains HEROES and PETS tabs, preserving the purchase and selection flow and showing the supplied portraits.

DEV CloudCode revision 33 changes only the three catalog names from revision 32 and preserves all 15 handlers. The local DEV account displayed the GH card as `NO OFFER`; no GH purchase was attempted. GH spend and relogin/device persistence remain unverified. PROD CloudCode remained revision 13 and received no V2 update. Before PROD release, use a GH-capable safe test environment, verify the native Store crypto charge, and merge pet handlers into the then-current PROD revision while preserving the GH payout maintenance guard and existing handlers.

After V2, a server-confirmed selection made during an active run immediately changes the visible companion (including switching or hiding it on unequip). The existing run keeps its original passive bonuses until the next `startStageRun` boundary. The PETS tab labels this distinction so the instant visual change does not imply an instant stat change. The client renders only IDs returned in `getPetState` and owned by the account; it never predicts a selection before the server responds.
