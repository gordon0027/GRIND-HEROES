# Grind Heroes Shop V1

The project already had the iDos Store module. It reads the player-resolved storefront through `client.store.getStorefront()`, and `client.store.purchase()` validates current slot, price, limits and rewards on the server. DEV currently has a daily free 30-GEMS gift, two GOLD offers priced in GEMS, and an Iron Sword offer priced in GEMS. The existing Store checkout remains under **MORE → Shop → SUPPLIES**. Its free gift and GEMS-priced supplies remain server-authoritative.

The screen now opens on **GEMS**, with **PREMIUM CHESTS** and **SUPPLIES** tabs. The first two tabs are presentation-only TOKEN products in `src/modules/store/shopCatalog.ts`: three Gem Packs and Rare, Epic and Legendary Chest concepts. Amounts and TOKEN prices are centralized, provisional DEV balancing figures. They are not Title Store offers and must not be published as final economy values. Cards use the existing GEMS icon and chest art, support optional badges, hide disabled entries, and open a details popup. The GEMS balance comes from the same `InventoryV2.VirtualCurrencies.GEMS.Amount` player state used by Marketplace, refreshed through the SDK cache.

`src/modules/store/tokenPurchase.ts` is the future purchase adapter boundary. BUY checks the configured product and returns `TOKEN_PROVIDER_NOT_IMPLEMENTED`; it performs no payment and grants nothing. The UI states this explicitly. No TOKEN balance is shown. DEV currently has no CryptoCurrency definition, no token checkout order flow, no premium chest offer, and no premium loot table. The existing `gear_summon` and stage/boss lootboxes open directly via `client.lootbox.open()` and are tied to existing GEMS or chest-item costs. None is silently repurposed as a premium chest. The Shop chest products intentionally hold a null fulfillment lootbox reference until authoritative definitions exist.

Future TOKEN → GEMS flow: resolve `productId` and price from a server-owned catalogue; create a purchase order; request wallet TOKEN payment; confirm transaction server-side; mark the order paid and credit GEMS server-side; refresh `InventoryV2` in the client. Future TOKEN → PREMIUM CHEST flow uses the same order and confirmation boundary, then server-side fulfillment grants an existing chest item or opens a configured premium lootbox, followed by an inventory refresh. The backend must select reward, amount, tier and price from its catalogue, never from client claims. A future order should track order ID, player ID, product ID, payment amount/currency, transaction signature and created/paid/fulfilled times with explicit pending, confirmed, fulfilled and failed states. No speculative order database or blockchain transaction is part of V1.

The DEV Title Store, Currency, Lootbox, Marketplace, Purchase, Item, Premium, Reward, Blockchain and CloudCode sections were inspected through MCP. Premium and Blockchain are empty. Reward has an automatic stage-chest item claim, not a premium purchase grant. No PROD configuration was changed. A local DEV-connected browser run checked the Shop on 391px and 1920px viewports, tab switching, art, details, BUY unavailable feedback, GEMS balance and the original Supplies shelf. Typecheck, build, the Shop boundary test and the existing test suite passed. Next work: define premium loot tables and a server-owned product catalogue/order service, implement and verify TOKEN payment confirmation on DEV, then replace `requestTokenPurchase` with that adapter.
