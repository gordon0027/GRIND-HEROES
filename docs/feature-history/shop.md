# Grind Heroes Shop V1

The project already had the iDos Store module. It reads the player-resolved storefront through `client.store.getStorefront()`, and `client.store.purchase()` validates current slot, price, limits and rewards on the server. DEV currently has a daily free 30-GEMS gift, two GOLD offers priced in GEMS, and an Iron Sword offer priced in GEMS. The existing Store checkout remains under **MORE → Shop → SUPPLIES**. Its free gift and GEMS-priced supplies remain server-authoritative.

The screen now opens on **GEMS**, with **PREMIUM CHESTS** and **SUPPLIES** tabs. TOKEN products in `src/modules/store/shopCatalog.ts` remain presentation-only until checkout exists. Amounts and TOKEN prices are centralized, provisional balancing figures, not final economy values. Cards use the existing GEMS icon and chest art, support optional badges, hide disabled entries, and open a details popup. The GEMS balance comes from the same `InventoryV2.VirtualCurrencies.GEMS.Amount` player state used by Marketplace, refreshed through the SDK cache.

`src/modules/store/tokenPurchase.ts` is the future purchase adapter boundary. BUY checks the configured product and returns `TOKEN_PROVIDER_NOT_IMPLEMENTED`; it performs no payment and grants nothing. The UI states this explicitly. No TOKEN balance is shown. DEV currently has no CryptoCurrency definition, token checkout order flow or premium loot table. The existing `gear_summon` and stage/boss lootboxes open directly via `client.lootbox.open()` and are tied to existing GEMS or chest-item costs. None is silently repurposed as a premium chest.

Future TOKEN → GEMS flow: resolve `productId` and price from a server-owned catalogue; create a purchase order; request wallet TOKEN payment; confirm transaction server-side; mark the order paid and credit GEMS server-side; refresh `InventoryV2` in the client. Future TOKEN → PREMIUM CHEST flow uses the same order and confirmation boundary, then server-side fulfillment grants an existing chest item or opens a configured premium lootbox, followed by an inventory refresh. The backend must select reward, amount, tier and price from its catalogue, never from client claims. A future order should track order ID, player ID, product ID, payment amount/currency, transaction signature and created/paid/fulfilled times with explicit pending, confirmed, fulfilled and failed states. No speculative order database or blockchain transaction is part of V1.

During Shop V1, the DEV Title Store, Currency, Lootbox, Marketplace, Purchase, Item, Premium, Reward, Blockchain and CloudCode sections were inspected through MCP. Premium and Blockchain were empty. Reward had an automatic stage-chest item claim, not a premium purchase grant. That pass did not change PROD configuration. A local DEV-connected browser run checked the Shop on 391px and 1920px viewports, tab switching, art, details, BUY unavailable feedback, GEMS balance and the original Supplies shelf. Typecheck, build, the Shop boundary test and the existing test suite passed.

New item instances default to upgrade level 1 and can follow the same upgrade path to level 10. Rarity controls the selected definition and the Grind required Hero Level (Rare 10, Epic 15, Legendary 20), not an extra hidden bonus. The chest item itself is nontradable; resulting equipment follows normal tradeability and can be listed on the GEMS Marketplace.

The local reference and provisional TOKEN price were not authoritative. No paid grant, TOKEN transaction, client reward roll or real premium chest open was performed in that pass. ## Token Purchase Orders V1 (2026-10-08)

The later user instruction remains **no DEV upload; PROD directly if publishing**. The PROD Title's native Store contains the existing free GEMS gift and GEMS-priced supplies. Purchase/Premium and DataCollections had no suitable TOKEN order records. iDos Data Collections therefore supplies persistent `gh_token_orders_v1` records; CloudCode owns creation and lookup. The collection is `UserOwned` and strict: only the server may create, update or delete; only the owner may read. Its order fields are server-written. Optional `paymentTxSignature` and `fulfillmentOperationId` have unique indexes. No client endpoint changes status, confirms payment or grants anything.

The authoritative product map lives in PROD CloudCode revision 6, sourced from `src/modules/store/server/tokenOrders.js`. Enabled IDs are `gems_small` (5 whole tokens → 500 GEMS), `gems_medium` (12 → 1,200 GEMS), `gems_large` (30 → 3,000 GEMS), and `premium_chest_v1` (20 → one `premium_chest_v1` Item, opened through `premium_equipment_v1`). These are initial order terms taken from Shop V1's provisional figures; payment remains disabled pending final pricing and treasury configuration. `chest_rare` and `chest_legendary` are disabled. The client Shop now fetches the server catalogue and holds only labels, art and order. Creating an order sends exactly `{productId, idempotencyKey}`; the server checks current Currency, Item and Lootbox definitions, resolves price and reward itself, then snapshots them. No rarity is selected. An existing order keeps its original terms when the catalogue changes.

PROD `Currency.CryptoCurrencies.Main` is active on Solana with mint `2gzmu2aJtyw35ph7wQhQKTKe9G6rwD91HyjjsEcJidos` and **0 configured decimals**. No token symbol or payment recipient was present in the inspected Title configuration or integration variables. The order records `Main`, Solana, mint, decimals and an exact integer base-unit amount string; the UI calls it the Grind Heroes token. No float amount is used. Because there is no recipient or payment verifier, new orders remain `CREATED` and the Pay button is disabled.

Each order has a unique stable ID derived from a UUID idempotency key, server-authenticated player ID, product and reward snapshot, status, creation time and a 20-minute expiry. Repeating the same key for the same player and product returns the stored order; a conflicting reuse is rejected. A read after expiry reports effective `EXPIRED` for unpaid `CREATED`/`AWAITING_PAYMENT` orders without changing their saved terms. Future payment code must check expiry independently before initiating or confirming payment. Defined transitions are `CREATED → AWAITING_PAYMENT → PAYMENT_SUBMITTED → CONFIRMED → FULFILLED`, with `FAILED`/`EXPIRED` terminal paths; none of the payment transitions is exposed to clients in V1. Future fulfillment must use the unique transaction signature, a server-only CAS/status transition and a stable idempotent resource-operation ID before granting exactly once.

A controlled PROD guest probe created one `gems_small` order and one `premium_chest_v1` order. Server responses were `CREATED`, with amounts `5` and `20` base units and the correct GEMS/chest references. Both could be read back by their owner. The guest's GEMS, TOKEN and item inventory snapshots were identical before and after. A local browser connected to PROD separately created a Gem Pack order and a Premium Chest order through Shop's BUY → confirm flow; both displayed their server snapshots and a disabled Pay button, with no browser-console errors. Local tests cover unknown/disabled products, malicious extra price/reward fields, owner isolation, retry, unique order IDs, price changes, expiration, transition boundaries and absence of resource grants. The normal Store and Marketplace configuration were not changed. Only PROD DataCollections and CloudCode were saved; DEV was untouched. The modified Shop client was built locally but not uploaded while unrelated working-tree changes are present.

Next checkout work: configure a trustworthy treasury recipient and final prices; return order ID, mint, recipient and exact base-unit amount; have the player sign a wallet transfer; independently verify its network, mint, recipient, amount, signature, order binding and confirmations; reserve the globally unique signature; CAS the order to `CONFIRMED`; grant GEMS or the chest once with a durable idempotency key; then mark `FULFILLED`. A client report of payment success must never grant a reward.

## Native TOKEN balance purchase inspection (2026-10-08)

The preceding "Next checkout work" was superseded by a read-only inspection of the iDos Store, Blockchain, Checkout, Currency and Lootbox MCP skills and the live PROD configuration. PROD `Currency.CryptoCurrencies.Main` is active, Solana-bound, has 0 on-chain decimals, and enables deposits, withdrawals and `SpendableInGame`. The platform page identifies its ticker as `GH`. The authoritative balance is `UserState.InventoryV2.CryptoCurrencies.Main.Amount` (a decimal string); `client.data.user.getCryptoCurrencyAmount("Main")` reads the SDK cache. The site has a wallet card for deposits and withdrawals. The platform wallet submits the on-chain transfer, then `client.blockchain.depositToken("solana", transactionHash)` reports it; the backend verifies the transaction and the configured 2 confirmations before crediting the in-game balance. This inspection did not submit a real deposit, so end-to-end operation for this title remains unverified. The game's baked `IDOS_WEB3 = false` and empty network ID mean its own wallet button is not enabled, and `WalletButton.tsx` is currently not rendered by the lobby. A Shop deposit action should open the platform wallet card when embedded and provide an appropriate direct-link wallet panel path.

The iDos Store supports a `ResourceConsume` price entry `{ Type: "CryptoCurrency", CurrencyID: "Main", Amount: N }`. Its `Reward.Grant.Standard.Entries` can grant `{ Type: "VirtualCurrency", CurrencyID: "GEMS", Amount: Y }` or `{ Type: "Item", CatalogID: "Item", ItemID: "premium_chest_v1", Amount: 1 }`. Each offer must be placed in a Store slot. `client.store.getStorefront()` supplies resolved offers and `client.store.purchase(offerID, 1, { selectedOptionID, slot })` performs one server-authoritative atomic resource operation with its purchase-counter writes. An offer purchase can atomically grant the chest item; Store does not expose a direct Lootbox-roll reward type. The subsequent `client.lootbox.open("premium_equipment_v1", 1, "chest")` consumes the item and rolls equipment in a separate atomic operation. If one-click TOKEN-to-equipment is required instead, adding a TOKEN `PriceOptions` entry to the Lootbox and calling `client.lootbox.open()` would make debit and roll one operation. `Main.Permissions.ConvertibleToVirtual` is true, but PROD defines no conversion targets, so `cryptoConvert()` is not currently an alternative for these fixed packs.

The Store SDK creates a fresh idempotency key per `purchase()` call; transport replay of one call is protected, while a double click creates two legitimate purchases. Disable BUY synchronously while pending. Store exposes per-offer purchase counters, but its server audit collection is not exposed through a Store history endpoint, and the documented `StorePurchaseResponse` does not promise a public order/receipt ID. Blockchain deposit history is separate (`client.blockchain.getTransactionHistory()`). PROD `Main` also references `Main_IOU`; the Currency skill says unbacked IOU is spent first when this crypto is spent, so final economy review should confirm that policy before selling paid goods. No TOKEN offers exist yet in PROD Store. The custom `gh_token_orders_v1` collection and CloudCode revision 6 remain live but only create unpaid orders; they duplicate the native balance-checkout path and should not be extended for this use case. Replace `tokenPurchase.ts`/`TokenShop.tsx` order creation with the resolved Store purchase API after configuring and reviewing PROD offer terms. No PROD settings, transactions or rewards were changed during this inspection; DEV was untouched.

## Premium Chest opening V1 (2026-10-08)

The in-game INVENTORY is the idle-rpg panel, separate from the generic Inventory module. It now shows a Premium Chest card using the same PNG as Shop and the `InventoryV2.Items.premium_chest_v1.StackableAmount` server-backed quantity. OPEN is disabled at zero or while pending. A synchronous ref gate rejects a second click before React can render the disabled state. The operation is exactly `client.lootbox.open("premium_equipment_v1", 1, "chest")`; Store purchase remains separate and never auto-opens. The PROD Lootbox's `MaxOpenCount` is 1, so the general Summons screen also cannot offer bulk Premium Chest opening. The six existing Stage/Boss lootbox definitions and pools are unchanged.

The response's resource grant identifies the server-rolled equipment Item ID. The UI re-reads `getUserInventory()`, waits for one new matching unstackable instance and for the chest count to decrease by one, then reveals that actual instance with the existing equipment art/rarity frame and shared stat row presentation. It does not choose rarity, slot or stats on the client or synthesize an item in local inventory. If the read lags, the opening remains in a syncing state with a retry button; an ambiguous transport failure keeps OPEN locked until reconciliation. A rejected opening re-reads inventory, preserves the quantity, shows an error and permits another attempt. Each click requests one chest only.

The first real economic purchase and opening are reserved for the player. Local tests and a non-economic PROD page check verify UI and integration, not an actual reward transaction. The result inherits normal equipment item definitions, including tradeability and Marketplace eligibility. The full self-contained client build with all 107 PNGs first went live on PROD as **v40**; its INVENTORY screen showed the Premium Chest image, server-backed ×0 count and disabled OPEN on a guest account. A follow-up **v41** added a focused stale-inventory reconciliation test and kept the same player flow. DEV was not uploaded.
